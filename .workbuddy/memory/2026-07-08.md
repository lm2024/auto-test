## 登录 500 排查结论(重要教训)
- 用户报 `AxiosError: status 500` 登录失败。经本机核实:`lsof :8080` 无监听、`curl` 登录接口返回空 → **后端进程根本没启动**。MySQL 容器 healthy,密码未改动(后端每次启动重置 admin→admin123)。
- **误诊教训**:vite proxy 对不可达的 `/api` 目标会返回 500(非 502),axios 捕捉到 `status 500`,容易被误判为"后端业务逻辑抛异常"。**不能单凭浏览器 500 推断后端在跑**;必须以本机 `lsof -nP -iTCP:8080 -sTCP:LISTEN` / 直接 `curl` 后端端口核实。
- 根因=后端未启动,与前端主题改造、密码无关。启动后端(`cd backend && mvn spring-boot:run`)即可。

## 批量执行提示"成功"与执行记录"失败"对不上（语义误导排查）
- **现象**:链路列表多选 → 批量执行,提示"执行启动: 2条成功,0条失败",但执行记录里是失败。
- **根因(非 bug,是语义误导)**:`/execute/batchRun` 对每个链路调 `executeService.runChain`,该方法仅校验链路/节点存在后插入 `status=RUNNING` 记录,再 `@Async` 异步执行节点(`ExecuteServiceImpl.runChain` 第84-113行),立即 `return executionId`。所以后端返回的 `status:"started"` 仅表示**任务成功提交/启动**,实际结果(SUCCESS/FAILURE)是后台线程跑完才写回。提示里的"成功"=提交成功,执行记录的"失败"=真实运行时失败,二者不同时间点、不同含义,自然对不上。
- **修复**:`frontend/src/views/ChainList.vue` 的 `batchExecute` 文案改为"已提交 N 条执行任务,最终结果请到「执行记录」中查看";若有链路启动失败(不存在/无节点)则 `ElMessage.warning` 提示被拒条数。不再用"成功/失败"混淆运行时结果。单条 `executeChain` 提示本就写"执行已启动",无需改。
- **可选后续(未做)**:若用户希望提示直接反映真实执行结果,需改为提交后轮询 `/execute/status` 直到非 RUNNING(链路本身仅 400~600ms,轮询可行),属较大改动,待用户确认。
