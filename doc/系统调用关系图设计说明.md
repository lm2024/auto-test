# 系统调用关系图设计说明

## 1. 设计目标

调用关系图是由测试链路、节点配置和系统注册表派生出来的分析视图，不直接把“边”当作一张可手工维护的孤立数据表。真实数据量达到十万级时，页面必须先检索和聚合，再展示有限范围的图形。

## 2. 数据职责

- 链路和节点的新增、修改、删除：在“测试链路”和节点编排页面完成。
- 系统编码、系统名称、网络范围、系统分类、域名规则：在“系统注册表”完成。
- 调用关系图：只读分析视图，按当前筛选条件实时派生。

这样可以避免同一条调用关系在多个页面重复维护，减少脏数据和删除联动问题。

## 3. 查询架构

`GET /api/call-graph/data` 支持：

- `keyword`：链路、系统、目标系统、URL 模糊检索
- `chainCode`：按链路过滤
- `scope`：INTERNAL / EXTERNAL / UNKNOWN
- `method`：HTTP 方法过滤
- `category`：系统分类过滤
- `pageNo`、`pageSize`：明细分页，服务端上限 100
- `maxNodes`：图形节点上限，服务端上限 500

接口返回两类数据：

1. 全量数据库聚合统计：调用总数、系统总数、网络范围、HTTP 方法、链路和系统排行。
2. 受控展示数据：当前页明细和最多 `maxNodes` 个图形样本。

页面不会把十万条原始记录加载到浏览器，也不会让 G6 force layout 处理十万节点。

## 4. 前端视图

- 调用网络：查看被测系统与目标系统的局部关系。
- 系统排行：定位调用量最高的系统。
- 链路排行：定位影响面最大的测试链路。
- 方法分布：观察 GET、POST 等协议行为。
- 调用明细：服务端分页，支持继续翻页检索。

图形样本被截断时页面明确显示“受控样本”，避免用户误以为图形代表全量关系。

## 5. 性能边界

- 搜索条件在数据库层执行。
- 统计使用 `COUNT` 和 `GROUP BY`，不依赖前端聚合。
- 图形默认最多 200 个节点，接口硬上限 500。
- 明细默认每页 20 条，最大每页 100 条。
- 系统注册表补齐 `category` 字段，并通过兼容初始化自动修复旧数据库。

后续如果调用数据继续增长，建议增加按天/版本的预聚合表，并为 `chain_code`、`interface_scope`、`request_method`、`target_system` 建立组合索引；当前页面已经具备切换到预聚合查询的接口边界。
