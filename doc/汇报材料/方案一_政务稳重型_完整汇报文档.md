## 一、汇报开篇（建议口述 2 分钟）

各位领导好。

今天汇报的是我们自主建设的**内网接口自动化测试平台**。这套系统的核心使命很明确：**把测试人员从重复的手工回归中解放出来，用自动化手段守住业务系统的稳态运行**。

它不是万能测试工具，而是精准定位于**既有功能的回归验证和稳态巡检**——这正是当前信息化建设「建得好、还要测得稳」的关键短板。

## 二、建设背景：领导为什么要关心这件事

### 2.1 宏观背景

- 业务系统持续迭代，接口数量快速增长，手工测试已难以支撑稳态保障要求
- 测试力量有限，大量精力消耗在重复回归，难以投入到更有价值的质量工作中
- 信息化建设不仅要「建得好」，更要「管得住、测得稳」

### 2.2 四大痛点（测试一线的真实困境）

| 序号 | 痛点 | 具体表现 |
|------|------|----------|
| 1 | 手工摘抄 | 测试人员从浏览器抓包，逐字段复制 URL、Header、Body 到测试工具，重复劳动多、易出错 |
| 2 | 依赖梳理 | 全链路接口参数依赖需人工梳理，上下游参数不匹配导致执行失败频发 |
| 3 | 数据构造 | 测试数据依赖人工编写，ID 递增、业务合规数据生成成本高 |
| 4 | 故障排查 | 接口执行失败后，需人工比对请求响应、定位根因，平均耗时 30-60 分钟 |

### 2.3 核心判断

> **成熟业务的稳态保障，不应依赖人海战术。回归自动化是信息化提质增效的关键抓手。**

## 三、平台定位（领导最关心的问题）

### 3.1 一句话定位

**「内网接口自动化测试平台 + 接口录制助手浏览器插件」** —— 让测试人员像操作业务页面一样，完成接口回归用例的建设与执行。

### 3.2 明确适用场景

| 维度 | 说明 |
|------|------|
| **核心定位** | 面向既有功能的回归验证与稳态保障 |
| **不是** | 新功能开发验证的主力工具 |
| **为什么适合回归** | 成熟业务流程路径固定，录制一次、反复执行，最适合版本发布前后的稳态巡检 |
| **能降低什么** | 将大量重复的手工接口回归，转化为「一键执行 + 自动比对」，显著压缩回归工作量 |
| **不适合什么** | 全新业务逻辑首次验证、复杂探索性测试、尚未稳定的频繁变更接口 |
| **推荐使用节奏** | 版本发布前跑全量回归；日常每周/每日稳态巡检；重大变更后定点回归 |

### 3.3 场景边界（主动说清楚，避免预期过高）

- 不做新功能首次验证的主力工具
- 不做复杂探索性测试、性能压测
- 不做大规模分布式集群
- **定位清晰，确保落地口碑**

## 四、核心能力与架构

### 4.1 三大模块

| 模块 | 技术栈 | 核心职责 |
|------|--------|----------|
| 后端服务 | JDK 8 + Spring Boot + MySQL + LangChain4j | 链路管理、自研执行引擎、日志存储、AI 能力、插件对接 |
| 前端平台 | Vue 3 + Element Plus + LogicFlow | 可视化拖拽编排、执行状态展示、AI 交互 |
| 浏览器插件 | Chrome/Edge Manifest V3 | 页面接口录制、跨页面持久化、一键推送平台 |

### 4.2 完整业务闭环

```
安装插件 → 开启录制 → 操作业务页面
    ↓
自动捕获接口 + 跨页面持久化存储
    ↓
人工筛选有效接口 → 自动识别上下游参数依赖
    ↓
一键推送平台 → 自动生成测试链路 + 节点 + 参数关联
    ↓
画布微调流程 → AI 生成测试数据 → 触发执行
    ↓
实时查看节点状态 → 失败一键 AI 分析 → 完整执行日志留存
```

### 4.3 自研执行引擎

- 支持全串行 + 分组并行两种执行模式
- 自动变量传递：上下游接口参数自动衔接
- 断言校验 + 完整日志：每次执行留痕，可追溯、可审计
- WebSocket 实时推送：执行过程全程可视

### 4.4 浏览器插件「接口录制助手」

- 测试人员正常操作业务页面，插件自动捕获全部接口请求
- 跨页面跳转不丢数据
- 一键推送至平台，自动识别参数依赖
- 无需编程、无需手工摘抄，半天即可上手

|------|------|------|

## 八、领导关切 · 问答备答（完整版）

### Q1：这个平台是干什么的？

**答：** 面向纯内网环境的接口自动化测试平台。解决测试人员「手工摘抄接口、人工梳理依赖、重复回归、失败难排查」四大痛点，把成熟业务的接口回归变成可录制、可复用、可一键执行的标准化能力。

### Q2：跟 Postman、JMeter 有什么区别？

**答：** 市面工具偏「单接口调试」，我们做的是「全链路闭环」：浏览器录制 → 自动识别参数依赖 → 可视化编排 → 批量执行 → 实时状态 → AI 排障。更重要的是完全适配纯内网、零中间件，测试人员不需要写代码。

### Q3：为什么更适合回归，而不是测新功能？

**答：** 回归场景业务路径已跑通、接口相对稳定，录制一次就能反复执行。新功能接口频繁变动、规则未定型，维护成本反而高。我们明确定位：做「稳态保障」和「回归减负」。

### Q4：能降低多少测试工作量？

**答：** 以 10 个接口的业务链路为例：手工回归每次约 2-3 小时，平台化后首次录制约 30 分钟，之后每次一键执行约 3-5 分钟。长期看，回归人力可压缩 70%-90%。

### Q5：测试人员好上手吗？

**答：** 不需要编程。装插件 → 操作业务页面 → 点「推送平台」→ 画布微调 → 点「执行」。普通测试人员半天即可独立操作。

### Q6：数据安全怎么保障？

**答：** 全程内网运行，数据不出网。AI 对接内网大模型。插件仅捕获指定业务域名请求，权限可控。

### Q7：部署复杂吗？

**答：** 单实例即可，仅需应用服务器 + MySQL，不需要 Redis、MQ。支持 Docker 部署。

### Q8：AI 是不是噱头？

**答：** 只做两个高价值场景：智能造数 + 失败诊断。且有规则降级，不影响基本使用。

### Q9：自动识别参数依赖准确吗？

**答：** 字段名一致时准确率很高。少量漏识别可在画布上人工补充，是可控的小偏差。

### Q10：版本升级后接口变了怎么办？

**答：** 重新录制或追加节点即可。新功能建议等接口稳定后再纳入回归库。

### Q11：能不能定时自动跑？

**答：** 当前手动触发为主，定时回归已规划为下一期能力。建议纳入发布流程统一触发。

### Q12：出了问题谁负责？

**答：** 自动化是「辅助判断」非「替代人工」。最终发布决策仍由测试负责人把关，平台提供完整日志和 AI 分析。

### Q13：投入产出比怎么样？

**答：** 小投入（无额外中间件采购）、大收益（回归人力大幅压缩）、快见效（2 周试点可出数据）。可落地性 97/100。

### Q14：未来还能做什么？

**答：** 定时回归、报告导出、条件分支编排、断点重跑、AI 变更影响分析等。

### Q15：现在就能用吗？

**答：** 核心闭环已完整实现，建议先选 1-2 条成熟链路试点，验证后逐步推广。
