# AI 驱动浏览器自动化测试 — 可行性研究报告

## 1. 概述

### 1.1 背景

本项目是一个 API 自动化测试平台，已具备以下能力：
- 浏览器插件 "捉接口 TraceFlow" 录制用户操作和 API 请求
- 后端流程执行引擎（串行/并行执行测试节点）
- AI 智能服务（基于 LangChain4j + OpenAiChatModel）
- WebSocket 实时推送
- 前端可视化链路编排

本次需求是在现有能力基础上，**增加 AI 驱动的浏览器自动化测试能力**，核心目标：
- 通过 AI 理解自然语言需求，自动生成浏览器操作脚本
- 通过 Playwright Java 驱动浏览器自动执行测试
- 支持定时自动执行和手动触发

### 1.2 文档目标

本报告旨在回答以下问题：
1. 当前技术栈（Java 8 + LangChain4j 0.35.0）能否支持？
2. 插件录制与 AI+Playwright 两条路径的关系是什么？
3. 具体技术方案是什么？能否落地？
4. 若可行，建议的落地策略是什么？

## 2. 技术可行性分析

### 2.1 Playwright Java 兼容性

| 维度 | 结论 | 依据 |
|------|------|------|
| Java 版本 | **完全兼容** | Playwright 官方文档明确要求 "Java 8 or higher" |
| Maven 依赖 | **可引入** | 坐标 `com.microsoft.playwright:playwright:1.44.0` |
| 浏览器驱动 | **自动管理** | Playwright 自动下载/管理 Chromium/Firefox/WebKit |
| 操作系统 | **兼容** | 支持 Windows 10+，当前 Windows 22H2 无问题 |

Playwright Java 提供完整 API：
- 页面导航、点击、填写、选择、截图、脚本注入
- 网络请求拦截与 mock
- 无头/有头模式切换
- 多标签页/多浏览器实例管理

**结论：Playwright Java 可安全引入，对 Java 8 无兼容风险。**

### 2.2 LangChain4j 0.35.0 兼容性

| 维度 | 结论 | 依据 |
|------|------|------|
| Java 版本 | **完全兼容** | parent POM 明确 `<maven.compiler.source>8</maven.compiler.source>` |
| 当前使用 | **已在用** | 项目已依赖 `langchain4j:0.35.0` 和 `langchain4j-open-ai:0.35.0` |
| 工具调用 | **低版本影响不大** | 本方案采用预生成脚本模式，不依赖实时 FC |

关键评估：LangChain4j 0.35.0 的 `OpenAiChatModel` 通过 `ChatRequest` API 工作正常，AI 脚本生成通过 SystemPrompt + 结构化输出即可实现，不依赖高版本的自动化工具调用循环。

**结论：LangChain4j 0.35.0 完全可支撑本方案，无需升级。**

### 2.3 AI 模型能力评估

当前对接的模型通过 Ollama 的 OpenAI 兼容 API 调用，配置为 `qwen-max`（实际可指定为 Qwen 3.5 122B）：

| 能力 | 是否支持 | 在本方案中的作用 |
|------|---------|----------------|
| 文本生成 | 支持 | 将自然语言需求转为操作脚本 |
| 结构化 JSON 输出 | 支持 | 生成规范的 action 序列 JSON |
| 图片理解（多模态） | 支持 | 分析 Playwright 截图，验证页面状态 |
| Function Calling | 支持 | 可通过 SystemPrompt 约束实现，但不作为主方案 |
| 长上下文 | 支持（128K+） | 可容纳完整操作脚本+截图分析 |

**结论：Qwen 3.5 122B 的文本和图片理解能力充分满足本方案需求。**

### 2.4 定时调度可行性

| 方案 | 复杂度 | 适用场景 |
|------|--------|---------|
| Spring `@Scheduled` 注解 | 极简 | 固定频率、固定 cron 的任务 |
| Spring `TaskScheduler` 编程式 | 中等 | 动态注册/取消定时任务 |
| Quartz 集成 | 复杂 | 集群化、持久化、高可用的调度 |

本方案需求为"用户在前端配置定时规则，后端按规则执行"，使用 **Spring `TaskScheduler` 编程式调度** 即可满足，充分利用项目已有的线程池配置（`executeThreadPool`）。

**结论：定时调度能力完整可落地。**

## 3. 两条路径的分析与定位

### 3.1 现有插件路径（捉接口 TraceFlow）

插件核心能力：
1. **API 录制** — 通过 `chrome.debugger` 捕获所有网络请求，记录 URL、方法、请求头/体、响应头/体、状态码
2. **宏录制** — 通过 `content.js` 录制用户点击、输入、选择、提交等操作，生成 macroActions
3. **宏回放** — 在浏览器页面内通过 DOM 操作模拟用户行为进行回放
4. **链路追踪** — 窗口状态机将用户交互与 API 请求关联为业务链路

插件录制的 macroActions 格式示例：
```json
[
  {
    "type": "navigate",
    "url": "https://example.com/login",
    "timestamp": 1700000000000
  },
  {
    "type": "click",
    "element": {"selector": "#username", "tag": "input"},
    "timestamp": 1700000001000
  },
  {
    "type": "input",
    "element": {"selector": "#username", "tag": "input"},
    "value": "testuser",
    "timestamp": 1700000002000
  }
]
```

### 3.2 新增 AI+Playwright 路径

新增能力：
1. **AI 脚本生成** — 用户输入自然语言（如"登录系统，创建用户，验证用户存在"），AI 生成操作脚本
2. **Playwright 执行引擎** — 后台无头浏览器自动执行操作脚本
3. **截图验证** — 执行过程中截图，AI 分析截图验证页面状态
4. **定时执行** — 按 cron 表达式自动触发执行

### 3.3 两条路径的差异与互补

| 维度 | 插件录制路径 | AI+Playwright 路径 |
|------|------------|-------------------|
| 驱动方式 | 人手动操作 + 录制 | AI 自动决策 + 执行 |
| 操作数据来源 | 真实用户行为 | AI 生成的脚本 |
| 执行环境 | 用户当前浏览器页面 | 后台无头浏览器 |
| 适合场景 | 首次构建链路、复杂交互、需要精准录制的场景 | 回归测试、定时执行、批量测试、数据驱动测试 |
| 操作精度 | 高（真实 DOM 操作） | 中高（选择器驱动） |
| 自动程度 | 半自动（人操作） | 全自动（AI 驱动） |

**关键发现：两者共享同一套 action 数据格式，可无缝互转。**

这意味着：
- 插件录制的操作脚本可直接导入 Playwright 回放
- AI 生成的操作脚本也可导出到插件环境执行
- 两条路径共存于同一个管理平台

### 3.4 用户工作流程整合

```
用户日常使用的两种模式：

【模式A - 录制模式】
插件开启录制 → 正常操作浏览器 → 插件捕获操作+API → 推送到平台 → 保存为BrowserTask
                                                                              ↓
【模式B - AI自动模式】                                             Playwright回放执行
用户输入需求 → AI生成脚本 → 人工确认/编辑 → 保存为BrowserTask → (手动/定时)执行
```

### 4.2 核心数据模型

统一 BrowserAction 格式（兼容现有 macroActions）：

```json
{
  "actionType": "navigate | click | input | select | check | submit | keypress | wait | screenshot | assert",
  "target": {
    "selector": "#username",
    "frame": null,
    "url": "https://..."
  },
  "value": "输入值",
  "options": {
    "delay": 500,
    "timeout": 10000,
    "waitAfter": 300
  },
  "description": "输入用户名"
}
```

### 4.3 预生成脚本模式流程

```
用户输入: "登录系统，进入用户管理页面，查看用户列表"

  {actionType: "navigate", target: {url: "https://example.com/login"}, description: "打开登录页"},

  {actionType: "input", target: {selector: "#password"}, value: "****", description: "输入密码"},
  {actionType: "click", target: {selector: "button[type='submit']"}, description: "点击登录"},
  {actionType: "wait", options: {delay: 2000}, description: "等待登录完成"},
  {actionType: "screenshot", description: "截图验证"},
  {actionType: "navigate", target: {url: "https://example.com/users"}, description: "进入用户管理"},
  {actionType: "wait", options: {delay: 1000}},

```

## 5. 结论

### 5.1 能做吗？—— **能，明确可行**

| 关键问题 | 结论 |
|---------|------|
| Java 8 + Spring Boot 2.7 能否支撑？ | 能，所有依赖均兼容 Java 8 |
| 插件录制能否与 AI+Playwright 共存？ | 能，共享同一套 action 数据格式 |
| Qwen 3.5 122B 能否支持图片分析？ | 能，通过 OpenAI 兼容 API 传输 base64 截图 |
| 定时自动化能否实现？ | 能，Spring TaskScheduler 编程式调度 |
| 现有工程是否需要大规模改造？ | 不需要，新增模块，不影响现有链路和引擎 |

### 5.2 怎么做？

分三轮落地：
1. **Phase 1（基础）**：Playwright 集成 + action 执行引擎 + 前端任务管理
2. **Phase 2（AI）**：AI 脚本生成 + 截图分析验证
3. **Phase 3（调度）**：定时任务 + 插件推送对接 + 批量执行

### 5.3 建议

**采取双路径策略**：保留现有插件录制能力不变，新增 AI+Playwright 路径，两者使用统一的 action 数据格式和任务管理界面。用户可根据场景灵活选择使用哪种方式创建和执行浏览器自动化测试。
