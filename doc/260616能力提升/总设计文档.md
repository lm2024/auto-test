# 浏览器插件录制能力增强 - 总设计文档

# 背景与目标

当前插件录制时，白名单内的所有请求（心跳、轮询、埋点、token刷新等）都会被捕获，用户无法区分哪些请求属于本次操作、哪些是无关干扰。导致一条用例混入大量无关接口，编辑成本高、回放不精准。同时存在统一认证跳转捕获、加密请求处理、测试账号管理、链路分类管理、插件交互体验等多项待增强能力。

核心目标：
1. 通过 bizOperTraceId + 时间滑动窗口 + 三重过滤，实现一次用户操作只产生一条纯净用例
2. 支持统一认证(SSO)场景下的多轮跳转 token 捕获
3. 支持加密请求的解密捕获
4. 平台具备测试账号管理能力，执行时自动绑定账号
5. 链路支持系统分类、功能分类
6. 插件交互体验优化（按钮状态、多选、AI评估）
7. 前端页面菜单可折叠/调整宽度

# 现状分析

当前 plugin-test 插件的录制流程：
1. inject.js 拦截 fetch/XHR/form，通过 postMessage 传给 content.js
2. content.js 转发给 background.js
3. background.js 通过 CDP debugger 补充捕获，写入 chrome.storage.local
4. 用户点"推送到平台"时，把 recordedApis 整体 POST 到后端 /api/plugin/chain/create

现有问题：
- 所有通过 shouldCapture(url) 白名单的请求全部记录，无操作级分组
- 无时间窗口概念，心跳/轮询等定时请求混入
- 无法区分"用户点击触发的请求"和"页面自行发起的请求"
- 后端无 bizOperTraceId 透传机制，前后端链路无法关联
- SSO 多轮跳转后的请求丢失认证信息
- 加密请求（如国密/AES/RSA）体内容不可读，无法断言
- 无测试账号管理，执行链路时无法绑定特定账号
- 链路无分类管理，数量多了无法快速定位
- 插件录制按钮状态不明确，停止后无反馈
- 链路管理只能单选，无法批量操作
- 前端左侧菜单固定不可折叠

# 设计方案总览

整体分八个模块：插件侧改造、统一认证与加密请求处理、后端透传机制、测试账号管理、链路分类管理、前后端链路聚合、录制面板交互增强、前端页面优化。参考 Katalon Recorder 的状态机管理、多定位器策略、持久化存储、沙箱执行等成熟设计。

# 模块一：插件侧 - bizOperTraceId 生成与注入

生成规则：
- 用户点击【开始录制】时生成唯一 bizOperTraceId，格式：biz_ + 时间戳 + 4位随机hex（如 biz_1718544000000_a3f2）
- 存入插件内存（变量），不持久化，录制结束时随数据一起推送
- 每次用户主动操作（click/change/keydown）生成新的子TraceId，格式：bizOperTraceId + _step序号（如 biz_1718544000000_a3f2_1）

注入规则：
- inject.js 拦截 fetch 时，在 Request 对象的 headers 中追加 X-Biz-Oper-Trace: ${bizOperTraceId}
- inject.js 拦截 XHR 时，在 open() 之后、send() 之前调用 setRequestHeader('X-Biz-Oper-Trace', ${bizOperTraceId})
- 每条被捕获的请求对象新增字段：bizOperTraceId、triggerEvent、targetDom、pageUrl、windowId

# 模块二：插件侧 - 时间滑动窗口 + 操作触发锁

触发条件（激活窗口）：
- 用户主动交互事件：click、change（select下拉）、keydown（回车）、submit（弹窗确认）
- 页面自动发起的请求（setTimeout/setInterval/页面onload）不触发窗口

窗口生命周期：
- 触发后开启窗口，初始持续时间 3 秒（可通过设置面板调整 2~5 秒）
- 窗口内出现新的业务接口请求（命中白名单），自动延长窗口，最长上限 5 秒
- 窗口超时无新业务请求 → 关闭窗口，封存当前链路

窗口状态机（参考 Katalon Recorder 的 RUN_MODE 状态管理）：
- IDLE → 用户交互触发 → ACTIVE
- ACTIVE → 收到新业务请求 → ACTIVE（重置倒计时）
- ACTIVE → 超时 → IDLE
- ACTIVE → 用户手动停止录制 → 完成封存

归属判定：
- 请求在窗口 ACTIVE 期间产生 且 携带当前 bizOperTraceId → 归属本次操作
- 请求在窗口 IDLE 期间产生 → 丢弃（即使命中白名单）

多操作切分：
- 第一次点击触发 TraceA，窗口 0~3s
- 间隔 6s（超过窗口阈值）再次点击 → 新建 TraceB，独立链路
- 两段操作彻底分开，形成两条独立用例

# 模块三：插件侧 - 三重过滤机制

第一重：黑白名单过滤（已有，保留）
- 静态资源（.js/.css/.png/.jpg 等）→ 直接丢弃
- 埋点上报（url 含 log/track/analytics/report）→ 标记为 track 类型
- 用户自定义黑名单域名/关键词 → 直接丢弃
- 白名单模式下仅保留匹配项

第二重：时间窗口过滤（本次新增，核心）
- 只有窗口 ACTIVE 期间的请求才进入候选集
- 窗口 IDLE 期间的请求（心跳、轮询、token刷新、前置加载）→ 自动剔除
- 这一重解决"10条里只3条相关"的核心问题

第三重：手动标记过滤（本次新增，兜底）
- 录制面板实时展示窗口内捕获的请求
- 自动推荐保留的请求：高亮显示
- 可疑无关请求（定时轮询、后台异步刷新）：标灰，提示用户确认
- 用户可一键取消勾选，该请求打上 ignore: true，回放时跳过

# 模块四：统一认证(SSO)与加密请求处理

统一认证挑战：
- 公司内统一认证可能涉及多轮跳转（CAS/OAuth2/SAML），每轮跳转产生新的域名请求
- 跳转后的请求携带的 token/cookie/session 与原始请求不同
- 插件需要在跳转链中持续捕获，不能因域名变化而丢失

SSO 多轮跳转捕获方案：
- inject.js 注册为最早执行（document_start），确保在跳转前注入拦截器
- 拦截器不因页面跳转而失效：通过 content.js + background.js 双层保活
- background.js 通过 CDP debugger 跟踪所有 tab 的网络请求，不依赖 inject.js 存活
- SSO 跳转链中的所有请求，通过 CDP 的 Network.requestWillBeSent 事件捕获
- 捕获到的认证信息（Set-Cookie 响应头、Authorization 请求头、token 参数）自动提取并存入上下文
- 下次回放时，先执行 SSO 登录流程获取新 token，再执行业务链路

Token 自动提取规则：
- 从响应头 Set-Cookie 提取 cookie 值
- 从请求头/响应头 Authorization 提取 Bearer token
- 从 URL 查询参数中提取 access_token、code 等
- 从响应体 JSON 中提取 token、refresh_token 等字段
- 提取到的 token 存入插件上下文，标记为"认证信息"

Token 过期处理：
- 录制时记录 token 过期时间（从 JWT payload 解析 exp 字段，或从响应 header 的 max-age 推算）
- 回放时检测 token 是否过期，过期则重新执行 SSO 登录流程
- 后端提供 /api/auth/token 接口，根据账号自动获取新 token

加密请求处理方案：
- 情况一：请求体加密但响应体明文 → 在 inject.js 拦截时，加密前的明文仍可捕获（fetch/XHR 拦截点在应用层加密之前）
- 情况二：请求体和响应体都加密 → 需要配置解密函数
- 情况三：HTTPS 流量加密（TLS）→ 浏览器扩展在应用层拦截，不受 TLS 影响

加密请求配置：
- 插件设置面板新增"加密请求处理"区域
- 用户可配置解密函数（JavaScript 函数），接收加密数据，返回明文
- 解密函数通过 iframe sandbox 执行（参考 Katalon Recorder 的 sandbox.js 沙箱模式），避免安全风险
- 配置项示例：请求体解密函数、响应体解密函数、加密算法标识（AES/RSA/SM4等）
- 默认不启用，用户按需配置

# 模块五：后端透传机制

拦截器设计：
- 新增 BizOperTraceFilter（OncePerRequestFilter），优先级最高
- 从请求头提取 X-Biz-Oper-Trace，放入 ThreadLocal
- 链路内 Feign/MyBatis 调用时，通过 ThreadLocal 拿到值注入下游请求头
- 请求结束时清理 ThreadLocal

数据存储：
- test_node_config 新增字段：biz_oper_trace_id（VARCHAR 64）
- 接口列表新增字段：trigger_event、target_dom、page_url、window_id
- 推送接口接收时一并入库

# 模块六：测试账号管理

核心需求：
- 平台统一管理各系统的测试账号，避免每人各用一个导致登录冲突
- 执行链路时自动绑定测试账号，回放时自动使用对应账号登录
- 支持多账号轮换，避免并发执行时账号冲突

数据模型（新增表 test_account）：
- id（主键）
- account_code（账号编码，唯一）
- account_name（显示名称）
- system_name（所属系统）
- username（登录用户名）
- password（登录密码，加密存储）
- auth_type（认证类型：SSO/PASSWORD/TOKEN/CERTIFICATE）
- auth_config（JSON，存储SSO登录地址、token接口等认证配置）
- status（状态：可用/禁用/锁定）
- last_used_time（最后使用时间）
- lock_until（锁定截止时间，并发执行时自动锁定）
- create_time、update_time

链路绑定账号：
- test_chain 新增字段：account_code（VARCHAR 64），关联绑定的测试账号
- 链路组（batch）执行时，按账号状态自动分配可用账号
- 账号被占用时自动锁定，释放后自动解锁

执行流程：
- 执行链路前，根据 chain 绑定的 account_code 获取账号信息
- 如果是 SSO 认证，先调用 auth_config 中的登录接口获取 token
- 将 token 注入后续所有请求的 Authorization 头
- 执行完成后释放账号锁定

# 模块七：链路分类管理

分类维度：
- 系统分类（system_category）：如"用户管理"、"订单系统"、"支付系统"、"审批流程"
- 功能分类（func_category）：如"登录认证"、"数据查询"、"数据新增"、"数据修改"、"数据删除"
- 优先级（priority）：P0核心回归、P1常规回归、P2低频验证

数据模型变更：
- test_chain 新增字段：system_category（VARCHAR 64）、func_category（VARCHAR 64）、priority（INT）
- 系统分类和功能分类使用字典表管理，支持用户自定义
- 新增表 dict_category（id、category_type、category_code、category_name、sort_order、status）

前端管理：
- 链路列表支持按系统分类、功能分类、优先级筛选
- 支持批量设置分类
- 分类信息在链路详情页展示
- 执行列表支持按分类查看执行结果

# 模块八：前后端链路聚合

聚合规则：
- 以 bizOperTraceId 作为分组主键
- 同一 bizOperTraceId 下的所有请求，按时间正序排列
- 前端操作事件 → 前端接口请求 → 后端HTTP入口 → 预留Dubbo调用 → 预留SQL语句
- 存储为一条"业务操作链路"，可整体回放

数据模型变更：
- test_chain 新增字段：biz_oper_trace_id（VARCHAR 64），关联一次操作的完整链路
- 一条 test_chain 可包含多个 bizOperTraceId（多次操作合并为一条链路）
- 回放时按 bizOperTraceId 分组，每组独立回放、独立断言

# 模块九：录制面板交互增强

按钮状态管理（参考 Katalon Recorder 的状态机设计）：
- 录制按钮明确三态：未录制（灰色）→ 录制中（红色脉冲）→ 已停止（绿色✓）
- 点击停止后，按钮旁显示"已停止"文字标签，持续 2 秒后恢复
- 宏录制按钮同理：三态明确，停止后有视觉反馈
- 新增录制状态指示器：sidepanel 顶部常驻显示当前录制状态（录制中/已停止/未录制）

链路管理多选：
- 链路列表新增复选框列，支持全选/反选
- 多选后显示批量操作栏：批量删除、批量推送、批量设置分类
- 参考 Katalon Recorder 的多文件导入设计，支持多链路批量操作

AI 链路评估（推送后自动分析）：
- 用户推送链路到平台后，后端自动触发 AI 评估
- 评估内容：
  1. 链路完整性：是否缺少关键步骤（如缺少登录、缺少数据清理）
  2. 无关请求识别：是否有疑似无关请求混入（心跳、轮询、埋点）
  3. 参数依赖分析：接口间的参数传递是否完整
  4. 重复请求检测：是否有重复的相同请求
  5. 优化建议：建议补充断言、建议参数化、建议拆分过长链路
- 评估结果展示在链路详情页，用户可采纳或忽略
- 参考当前项目已有的 AiServiceImpl（/api/ai/data/generate），复用 AI 调用能力

录制面板新增展示：
- 实时显示当前窗口状态（ACTIVE/IDLE），用颜色区分
- 每条请求显示归属的 bizOperTraceId 和触发事件类型
- 按 bizOperTraceId 分组展示，用户可折叠/展开
- 可疑请求标灰并提示"疑似无关（定时轮询）"
- 一键取消勾选功能，打上 ignore 标记
- 录制结束后自动按 bizOperTraceId 分组推送到后端

左侧菜单折叠：

# 前后端字段变更清单

插件侧新增字段（每条请求对象）：
- bizOperTraceId（string）- 操作级TraceId
- windowId（string）- 窗口ID，同一次操作的请求共享
- triggerEvent（string）- 触发事件类型：click/change/keydown/submit/auto
- targetDom（string）- 操作DOM标识：按钮id/选择器
- pageUrl（string）- 当前页面地址
- windowActive（boolean）- 是否在窗口激活期间产生
- ignore（boolean）- 用户手动标记忽略
- decryptedBody（string）- 解密后的请求体（如有）
- decryptedResponse（string）- 解密后的响应体（如有）

后端新增字段/表：
- test_chain 表：biz_oper_trace_id（VARCHAR 64）、account_code（VARCHAR 64）、system_category（VARCHAR 64）、func_category（VARCHAR 64）、priority（INT）
- test_node_config 表：biz_oper_trace_id（VARCHAR 64）、trigger_event（VARCHAR 32）、target_dom（VARCHAR 256）、page_url（VARCHAR 512）、window_id（VARCHAR 64）、ignore（TINYINT）
- 新增 test_account 表（测试账号管理）
- 新增 dict_category 表（分类字典）

# 与现有架构的兼容性

向后兼容：
- 不带 X-Biz-Oper-Trace 头的请求，后端 Filter 不处理，走原有逻辑
- 旧版本插件推送的数据，新字段为空，不影响已有用例
- 新旧版本可并行使用，无破坏性变更
- 测试账号管理为可选功能，不绑定账号的链路按原有方式执行

分阶段实施：
- 阶段一（核心）：插件侧 bizOperTraceId 生成 + 时间窗口 + 三重过滤 + 按钮状态修复
- 阶段二（后端）：后端 Filter 透传 + 数据库存储 + 测试账号管理
- 阶段三（面板）：录制面板交互增强 + 多选 + 分类管理 + AI 评估
- 阶段四（高级）：SSO 自动登录 + 加密请求解密 + 前端菜单优化
- 阶段五（聚合）：前后端链路聚合 + 按 TraceId 分组回放

# 参考 Katalon Recorder 的设计借鉴

从 Katalon Recorder v7.1.0 中可借鉴的成熟设计：

1. 状态机管理：三态模式（IDLE/OBJECT_SPY/RECORDER）明确区分录制状态，我们的 bizOperTraceId 窗口状态机参考此设计

2. 多定位器策略：KULocatorBuilders 提供 14+ 种元素定位策略（XPath/CSS/ID/name等），我们的宏录制可借鉴多策略容错

3. 持久化存储：三重冗余（storage.local > storage.sync > cookies），我们的插件设置可参考此方案

4. 沙箱执行：sandbox.js 通过 iframe 隔离 eval 执行，我们的加密请求解密函数执行参考此方案

5. 上下文菜单：右键菜单操作链路的交互方式，可应用于插件链路管理

6. 多选批量操作：测试用例的多选导入、批量执行设计，应用于我们的链路批量操作

7. 自修复机制：当定位器失败时自动尝试备选定位器，我们的宏回放可借鉴此设计

8. Keep-Alive 机制：通过 setInterval 定期调用 getPlatformInfo 保活 service worker，我们的 background.js 需要此机制

9. 外部扩展接口：通过 onMessageExternal 注册能力，我们的插件可预留扩展接口供其他工具调用

10. 导入导出格式：支持多种格式导出（JSON/Puppeteer/Protractor等），我们的链路可参考多格式导出

# 专家方案评估结论

评估结果：方案可行，核心思路正确，根据项目实际情况和新增需求做以下补充调整：

1. bizOperTraceId 生成位置：同意专家方案，只在浏览器插件生成，服务端透传。当前项目无 Dubbo，后端 Filter 透传到 Feign/MyBatis 即可。

2. 时间滑动窗口：同意方案，初始窗口建议 3 秒、最长 5 秒。当前项目无 WebSocket 拦截需求，窗口仅覆盖 HTTP 请求。

3. 三重过滤：同意方案。当前项目已有黑白名单（shouldCapture），在此基础上叠加窗口过滤和手动标记即可。

4. MDC 透传：当前项目无 SkyWalking/Jaeger，暂不需要 MDC 透传。用 ThreadLocal 存储 bizOperTraceId，后续如需接入链路监控再扩展。
