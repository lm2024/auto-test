## 1. 一句话讲清这个插件

**Katalon Recorder 是一个"把用户在浏览器里的 DOM 事件翻译成 Selenese 命令表、再把命令表逐条翻译回浏览器操作"的双向翻译器。**

它不是录网络请求的，也不是录像的。它录的是**语义层的用户意图**：你点了哪个元素、往哪个输入框敲了什么、选了哪个下拉项。所以你看到的是 `click | xpath=//button[@id='login']`，而不是 47 条 XHR。

## 2. 最反直觉的一件事：后台不在 Service Worker 里

这是理解整个工程的**总钥匙**。绝大多数人（包括我最初）会假设：MV3 扩展 = Service Worker 当后台。**KR 不是这样。**

```
                          ┌─────────────────────────────────────────┐
                          │   Service Worker (worker_wrapper.js)    │
                          │   —— 只是个"权限跑腿"                    │
                          │   · chrome.windows.create 开面板         │
                          │   · chrome.contextMenus 右键菜单         │
                          │   · chrome.debugger CDP（上传/按键）      │

                          └───────────────┬─────────────────────────┘
                                          │ 一次性握手
                                          │ {selfWindowId, commWindowId}
                                          ▼
┌──────────────────────────────────────────────────────────────────────────┐
│           Panel 独立窗口  panel/index.html  (1080×630, type:"popup")       │
│           ★★★ 真正的后台大脑在这里 ★★★                                    │
│                                                                          │
│  panel/js/background/recorder.js          ← BackgroundRecorder（录制状态机）│
```

### 为什么这么设计？

| MV3 的限制 | Service Worker 做不了 | KR 的对策 |
|---|---|---|
| SW 空闲 30 秒被杀 | 录制状态机会丢 | 把状态机搬进长驻 Panel 窗口 |
| SW 没有 DOM | 没法渲染命令表格 | Panel 是真实页面，有完整 DOM |
| SW 没有 `window.prompt()` | `storeXxx` 命令没法弹输入框 | Panel 里能弹 |
| SW 没有 `getBackgroundPage()` | Panel 拿不到后台引用 | **不需要拿——Panel 自己就是后台** |

**证据**：`worker_wrapper.js:1-26` 的 `importScripts` 清单里**没有** `recorder.js`、**没有** `window-controller.js`、**没有** `playback/`；而 `panel/index.html:1001-1016` 把它们全部 `<script type="module">` 引了进来。

> 💡 **复刻第一原则**：不要试图把录制/回放逻辑放进 Service Worker。用一个 `chrome.windows.create({type:"popup"})` 开出来的独立窗口当后台，是 MV3 下成本最低、最稳的路径。

## 3. 五个执行上下文速查表

| # | 上下文 | 载体文件 | 有 `chrome.*` 吗 | 有 DOM 吗 | 生命周期 | 主要职责 |
|---|---|---|---|---|---|---|
| 1 | Service Worker | `worker_wrapper.js` | ✅ 全量 | ❌ | 事件驱动，30s 空闲回收 | 开窗、菜单、CDP、截图、offscreen |
| 2 | **Panel 窗口** | `panel/index.html` | ✅ 全量 | ✅ | 用户关闭前长驻 | **录制状态机 + 回放引擎 + UI** |
| 3 | Content ISOLATED | 3 个脚本 | ✅ 全量 | ✅（隔离） | 随页面 | polyfill + RPC server |
| 4 | Content MAIN | `bundles/content.1.bundle.js` | ❌ **需 RPC 代理** | ✅（页面原生） | 随页面 | 事件捕获、定位器生成、Selenium API |
| 5 | Offscreen / Sandbox | `panel/offscreen.html` / `panel/sandbox.html` | 部分 | ✅ | 按需创建即用即关 | 指纹埋点 / 合规 `eval` |

### 为什么录制器要跑在 MAIN world？

ISOLATED world 拿不到页面自身的 JS 对象（React 实例、jQuery、自定义事件）。跑在 MAIN world 才能：
- 拿到页面原生的 `document` 与事件对象（不是隔离副本）
- 读取框架挂在 DOM 上的属性（如 `__reactProps$xxx`）
- 让 `selenium-api.js` 的 `eval` 类命令在页面真实作用域执行

**代价**：MAIN world 没有 `chrome.runtime`。KR 用一套自研的 `RemoteObjectHelper`（`common/remote-object-helper-page.js` / `-content.js`，各 97KB）通过 `window.postMessage` 做 RPC 代理，把 `chrome.runtime` / `chrome.storage` / `chrome.extension` 三个命名空间"投影"进 MAIN world。

⚠️ 安全缺陷：密钥是**明文硬编码**的 `"pandoraboz"`，且 `postMessage(..., "*")` 不校验 origin。同页任何第三方脚本都能伪造消息拿到 `chrome.storage` 完整读写权。复刻时必须换成随机 nonce。

## 4. 两条主链路的完整数据流

### 4.1 录制链路（用户点击 → 表格里出现一行）

```
① 用户在页面上 click
      ↓  （capture 阶段监听，不是 bubble）
② content/recorder.js  eventHandlers["C_click"]
      ↓
③ LocatorBuilders / KULocatorBuilders 生成候选定位器数组
      ↓  targets = [["xpath=//button[@id='login']","xpath:attributes"],
      ↓             ["css=#login","css"], ["id=login","id"], ...]
④ recorder.record("click", targets, "")
      ↓  过滤掉 #popupInjectionKR（录制浮层自身）
⑤ browser.runtime.sendMessage({command,target,value,frameLocation})   ← 广播
      ↓
⑥ Panel: panel/js/background/recorder.js  addCommandMessageHandler(msg, sender)
      ↓  用 sender.tab.id 判断是不是新窗口 → 自动补 open / selectWindow
      ↓  用 msg.frameLocation 做差分 → 自动补 selectFrame
⑦ addCommandAuto("click", targets, "")
      ↓
⑧ records-grid 新增一行 <div id="records-N">，双层 div 存 real/show 值
```

### 4.2 回放链路（点 Play → 页面上元素被点）

```
① 用户点 Play
      ↓
② panel/js/background/playback/  executionLoop 取第 N 条命令
      ↓
③ preprocessParameter 替换 ${var}
      ↓
④ window-controller.js  sendCommand("click", target, value)
      ↓  retryUntilSuccess(fn, 60, 500)  ← 30 秒重试上限
⑤ browser.tabs.sendMessage(tabId, {commands,target,value}, {frameId})  ← 定向
      ↓
⑥ content/command-receiver.js  doCommands()
      ↓  "click" → 首字母大写 → selenium["doClick"]
⑦ content/selenium-api.js  Selenium.prototype.doClick(locator)
      ↓  browserbot.findElement(locator) → 真实 DOM 操作
⑧ 结果回传 → sideex_log.info("...")  → 日志面板
      ↓  失败时 → getPossibleTargetList() → 自愈重试
```

## 5. 用户最初的三个疑问，在这里回答

### Q1：为什么显示的是我的事件，而不是一堆网络请求？

**因为 KR 根本没申请 `webRequest` 权限**（`manifest.json` 的 permissions 里没有），它工作在 **DOM 事件层**，不是 network 层。DevTools 的 Network 面板抓的是 HTTP 流量，KR 抓的是 `addEventListener('click', handler, true)`。两者在不同的抽象层。

一次"点击登录按钮"在 network 层可能是 1 次 POST + 12 次静态资源 + 3 次埋点上报；在 DOM 事件层就是**一个 click 事件**。

→ 详见 `tech/TECH-01-录制引擎.md` 第 3.4 节

### Q2：为什么能识别"是什么事件"？

因为有一张**事件 → 命令的语义映射表**，并且做了三层收敛：

1. **白名单**：只监听 click / change / select / keydown / submit 等有语义的事件，其余全部忽略
2. **入口守卫**：`input` 事件只记录"哪个元素正在被输入"，**不产命令**；等 `change` 事件（失焦或回车）才落一条 `type`。所以敲 10 个字符只出 1 条命令
3. **状态机**：`preventType` / `preventClick` 等标志位防止同一次交互被多个 handler 重复记录

→ 详见 `tech/TECH-01-录制引擎.md` 第 4 节（含完整合并总表）

### Q3：为什么能调整顺序？日志旁边那些功能是什么？

命令表格是纯前端 DOM（`records-grid`），每行是 `<div id="records-N">`，用 jQuery UI `sortable` 实现拖拽，拖完 `re-assign-id` 重排编号并同步数据模型。

底部五个标签页：
| 标签 | 干什么 | 数据来源 |
|---|---|---|
| **Log** | `sideex_log` 对象的输出，`[info]/[error]/[debug]` | 回放引擎逐条写入 |
| **Screenshots** | 回放中 `captureEntirePageScreenshot` 抓的图 | Content → SW `tabs.captureVisibleTab` |
| **Variables** | 回放期 `${var}` 的实时值 | `storeXxx` 命令回传 |
| **Reference** | 当前选中命令的参数说明文档 | Selenium API 元数据 |
| **Self-healing** | 自愈记录表 + Approve 按钮 | 回放失败时切换定位器成功的记录 |

→ 详见 `tech/TECH-04-PanelUI与日志.md` 第 5 节和第 8 节

## 8. 打包机制（一个容易踩的坑）

`bundles/content.1.bundle.js` **不是 webpack 产物**，而是**纯文本按顺序拼接**，文件内用 `/// File: xxx.js` 注释分隔。

对应关系可以从 `manifest.bak.json`（未打包版 manifest，构建残留）反推出来：

```json
// manifest.bak.json:106-126  →  打包成 content.1.bundle.js
"js": [
  "content/bowser.js", "content/atoms.js", "content/utils.js",
  "content/selenium-commandhandlers.js", "content/selenium-browserbot.js",
  "common/escape.js", "content/selenium-api.js",
  "content/neighbor-xpaths-generator.js", "content/locatorBuilders.js",
  "content/recorder.js", "content/recorder-handlers.js",
  "content/command-receiver.js", "content/targetSelecter.js",
  "content/sizzle.js", "content/kar.js"
]
```

> 💡 `manifest.bak.json` 是整个逆向过程中**最有价值的一个文件**——它保留了打包前的完整脚本清单和注入顺序，等于官方给的架构说明书。建议在裁剪前先归档它。

**MAIN world 的注入顺序是硬约束**：
```
remote-object-helper-page.js  →  chrome-polyfill.js（造出 chrome.runtime.id）
                              →  browser-polyfill-page.js
```
顺序错了 `webextension-polyfill` 会因为 `chrome.runtime.id` 为空直接 `throw`。
