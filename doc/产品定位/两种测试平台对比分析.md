# 两种测试平台对比分析

## 一、两种平台概述

### 平台A：录制驱动型（本项目 ApiCraft/链测）

**核心理念：** 从真实用户操作出发，录制→生成→执行

- 通过浏览器插件录制页面操作，捕获实际网络请求
- 自动识别上下游参数依赖，一键生成测试链路
- 可视化拖拽编排，AI辅助数据生成与故障分析
- 纯内网部署，零外网依赖

### 平台B：AI驱动型（公司另一项目）

**核心理念：** 从接口文档出发，AI生成→脚本执行

- 从业务系统获取 Swagger/OpenAPI 接口文档
- AI 将接口信息转化为 Python 测试脚本
- 支持手动触发、定时触发、AI触发三种执行方式
- 重AI能力，强调智能化测试生成

---

## 二、核心区别对比

### 2.1 测试数据来源

| 维度 | 平台A（录制驱动） | 平台B（AI驱动） |
|------|-------------------|-----------------|
| **数据来源** | 浏览器录制的真实请求 | Swagger/OpenAPI 接口文档 |
| **数据真实性** | ✅ 100%真实请求，包含完整参数值 | ⚠️ 文档定义的参数结构，需AI构造参数值 |
| **参数依赖** | 自动识别实际调用链路中的参数传递 | 需要AI推断或人工定义参数关系 |
| **覆盖范围** | 仅覆盖前端调用的接口 | 可覆盖所有文档定义的接口（含内部接口） |
| **维护成本** | 页面改版后需重新录制 | 接口文档更新后自动同步 |

**结论：** 两种方式互补而非替代。录制抓真实场景，Swagger补全覆盖盲区。

### 2.2 测试生成方式

| 维度 | 平台A（录制驱动） | 平台B（AI驱动） |
|------|-------------------|-----------------|
| **生成方式** | 录制→参数依赖识别→链路模板 | Swagger→AI解析→Python脚本 |
| **生成产物** | 可视化流程图 + 节点配置 | Python测试脚本 |
| **可编辑性** | ✅ 画布拖拽，零代码编辑 | ⚠️ 需修改Python代码 |
| **AI参与度** | 辅助（数据生成、故障分析） | 核心（全流程AI生成） |
| **学习曲线** | 低（可视化操作） | 中（需理解脚本逻辑） |
| **灵活性** | 受限于预设节点类型 | 高（Python可实现任意逻辑） |

### 2.3 执行触发方式

| 维度 | 平台A（录制驱动） | 平台B（AI驱动） |
|------|-------------------|-----------------|
| **手动触发** | ✅ 画布点击执行 | ✅ 手动运行脚本 |
| **定时触发** | ❌ 本期不包含 | ✅ 定时任务调度 |
| **AI触发** | ❌ 无 | ✅ AI判断何时执行 |
| **CI/CD集成** | 待扩展 | 更易集成（脚本化） |
| **批量调度** | 待扩展 | ✅ 多脚本批量执行 |

**结论：** 平台B在执行调度上更成熟，平台A侧重单链路的精细化执行。

### 2.4 技术架构差异

| 维度 | 平台A（录制驱动） | 平台B（AI驱动） |
|------|-------------------|-----------------|
| **核心语言** | Java + JavaScript | Python |
| **执行引擎** | 自研Java执行引擎 | Python脚本直接执行 |
| **状态管理** | 数据库存储 + WebSocket推送 | 脚本内部状态管理 |
| **并发模型** | 线程池 + 异步执行 | Python多进程/异步 |
| **部署方式** | 单实例Java应用 | Python环境 + 调度器 |
| **扩展性** | 受限于Java生态 | Python生态丰富（pytest等） |

### 2.5 用户角色适配

| 维度 | 平台A（录制驱动） | 平台B（AI驱动） |
|------|-------------------|-----------------|
| **目标用户** | 测试工程师（零编码） | 测试开发工程师（会Python） |
| **上手门槛** | ⭐ 低（30分钟） | ⭐⭐ 中（需Python基础） |
| **日常操作** | 录制→编排→执行 | 维护脚本→调度执行 |
| **问题排查** | 可视化节点状态 + AI分析 | 查看脚本日志 + Python调试 |
| **适合场景** | 业务回归测试、冒烟测试 | 接口压测、复杂逻辑验证 |

## 三、产品定位差异

### 3.1 平台A定位：轻量化业务回归测试工具

**一句话定位：** 录制即链路，零编码的接口回归测试平台

**核心价值：**
- 降低测试门槛，让普通测试人员也能做自动化
- 录制替代手工抓包，效率提升10倍
- 可视化编排，流程一目了然
- 纯内网，数据安全可控

**差异化优势：**
1. 录制驱动，数据100%真实
2. 可视化零代码，30分钟上手
3. 参数依赖自动识别
4. 纯内网AI，数据不出网

**不适合场景：**
- 复杂逻辑的接口测试（需条件分支、循环）
- 性能压测
- 需要精细控制的批量调度

### 3.2 平台B定位：AI驱动的智能测试平台

**一句话定位：** AI生成脚本，智能化的接口测试与调度平台

**核心价值：**
- AI自动化程度高，从文档到脚本全自动生成
- 定时调度能力强，适合持续集成
- Python脚本灵活性高，可实现任意复杂逻辑
- AI触发执行，智能化运维

**差异化优势：**
1. Swagger驱动，接口覆盖全面
2. Python脚本，灵活性极高
3. 定时/AI触发，调度能力强
4. 可集成CI/CD流水线

**不适合场景：**
- 零编码需求（需Python基础）
- 需要真实用户场景的回归测试
- 对数据真实性要求极高的场景

## 四、设计思路差异

### 4.1 核心设计哲学

| 维度 | 平台A（录制驱动） | 平台B（AI驱动） |
|------|-------------------|-----------------|
| **设计哲学** | **用户视角** — 从真实操作出发 | **文档视角** — 从接口定义出发 |
| **自动化理念** | 工具辅助人，人做决策 | AI替代人，自动决策 |
| **测试模型** | 场景驱动（用户做了什么） | 接口驱动（接口能做什么） |
| **AI定位** | 辅助角色（生成数据、分析故障） | 核心角色（生成脚本、触发执行） |

### 4.2 架构设计差异

#### 平台A架构：三端分离 + 中心化执行

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  浏览器插件  │───▶│  前端画布   │───▶│  后端服务   │
│  (录制数据)  │    │ (可视化编排) │    │ (执行引擎)  │
└─────────────┘    └─────────────┘    └─────────────┘
                          │                   │
                          ▼                   ▼
                   ┌─────────────┐    ┌─────────────┐
                   │  节点配置   │    │  执行日志   │
                   │  (数据库)   │    │  (数据库)   │
                   └─────────────┘    └─────────────┘
```

**特点：**
- 三端解耦，各自独立演进
- 执行引擎中心化，状态统一管理
- 数据库存储所有配置，支持版本管理
- WebSocket实时推送执行状态

#### 平台B架构：AI中心 + 脚本执行

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│ Swagger文档  │───▶│   AI 引擎   │───▶│ Python脚本  │
│  (接口定义)  │    │  (生成脚本)  │    │  (测试执行)  │
└─────────────┘    └─────────────┘    └─────────────┘
                          │                   │
                          ▼                   ▼
                   ┌─────────────┐    ┌─────────────┐
                   │  触发调度   │    │  执行报告   │
                   │ (定时/手动)  │    │  (脚本输出)  │
                   └─────────────┘    └─────────────┘
```

**特点：**
- AI是核心引擎，负责生成与决策
- 脚本化执行，灵活性高
- 调度器独立，支持多种触发方式
- 报告基于脚本输出，可定制性强

### 4.3 数据流差异

#### 平台A数据流：录制 → 模板 → 执行

```
真实操作 → 插件录制 → 参数识别 → 链路模板 → 执行引擎 → 结果日志
   ↑                                                      │
   └──────────────── 人工确认/调整 ◀───────────────────────┘
```

**关键点：**
- 数据来自真实操作，可信度高
- 模板可复用，支持版本管理
- 人工确认环节，可控性强

#### 平台B数据流：文档 → 脚本 → 执行

```
Swagger文档 → AI解析 → Python脚本 → 调度触发 → 执行结果
      ↑            │
      └────────────┘
      AI自主迭代优化
```

**关键点：**
- 数据来自文档，覆盖全面
- AI自主生成，自动化程度高
- 可定时/AI触发，无人值守

### 4.4 扩展性设计差异

| 维度 | 平台A（录制驱动） | 平台B（AI驱动） |
|------|-------------------|-----------------|
| **新接口类型** | 需开发新节点组件 | Python脚本可处理任意类型 |
| **复杂逻辑** | 受限于预设节点 | Python可实现任意逻辑 |
| **第三方集成** | 需后端开发接口 | Python生态丰富，易集成 |
| **性能测试** | 不支持 | 可集成locust等工具 |
| **报告定制** | 固定格式 | Python可生成任意格式 |

## 五、适用场景建议

### 5.1 选择平台A（录制驱动）的场景

- ✅ 业务回归测试（确保核心流程不出问题）
- ✅ 冒烟测试（新版本快速验证）
- ✅ 测试团队编码能力弱（零编码需求）
- ✅ 需要真实用户场景（录制100%真实）
- ✅ 对数据真实性要求高（不接受AI构造的数据）
- ✅ 接口数量不多（几十到几百个）

### 5.2 选择平台B（AI驱动）的场景

- ✅ 接口数量多（几百到几千个）
- ✅ 需要定时回归（每天/每周自动执行）
- ✅ 测试团队有Python基础
- ✅ 需要复杂逻辑测试（条件分支、循环）
- ✅ 需要集成CI/CD流水线
- ✅ 需要性能压测
- ✅ Swagger文档完善

### 5.3 两种平台协同使用

**最佳实践：** 两种平台互补使用

```
日常回归：平台A（录制驱动）
├── 核心业务流程录制
├── 冒烟测试执行
└── 新版本验证

深度测试：平台B（AI驱动）
├── 全量接口覆盖
├── 定时回归调度
├── 复杂场景测试
└── CI/CD集成
```

## 六、总结

| 维度 | 平台A（录制驱动） | 平台B（AI驱动） |
|------|-------------------|-----------------|
| **核心能力** | 录制 + 可视化编排 | AI生成 + 脚本执行 |
| **目标用户** | 测试工程师（零编码） | 测试开发（会Python） |
| **自动化程度** | 半自动化（人机协作） | 高度自动化（AI驱动） |
| **灵活性** | 中等（受预设限制） | 高（Python无限制） |
| **上手门槛** | 低（30分钟） | 中（需Python基础） |
| **数据来源** | 真实录制 | Swagger文档 |
| **执行调度** | 手动触发 | 手动/定时/AI触发 |
| **适合场景** | 业务回归、冒烟测试 | 接口全覆盖、持续集成 |

**一句话总结：**
- 平台A是**"让人更高效地测试"** — 工具辅助，人做决策
- 平台B是**"让AI自动测试"** — AI主导，自动执行

两者不是竞争关系，而是互补关系。根据团队能力、测试场景、数据来源选择合适的平台，或两者协同使用。
