# 分类管理大数据性能设计

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 功能 | 多级分类管理与分类引用 |
| 适用规模 | 约 10 万叶子节点，支持多级分类 |
| 前端 | Vue 3、TDesign Tree |
| 后端 | Spring Boot、MyBatis、MySQL 8 |
| 当前模型 | `sys_category.parent_id` 邻接表模型 |
| 状态 | 当前优化方案说明与后续增强设计 |

## 2. 背景与目标

公司分类数量较大，叶子节点预计约 10 万个。传统的“查询整棵树、前端递归组装、默认全部展开”方案会造成以下问题：

- 首屏接口响应体过大，网络传输时间不可控。
- 浏览器一次性创建大量 JavaScript 对象和 DOM 节点。
- 前端搜索需要扫描整棵树，输入卡顿明显。
- 父分类过滤需要把全部子分类 ID 加载到应用内存，容易产生超长 SQL。
- 分类选择器、定时任务、执行记录等页面重复加载分类数据。

本设计目标：

1. 首屏不加载完整分类树。
2. 分类展开只查询当前父节点的直接子节点。
3. 搜索由后端执行，并限制返回数量。
4. 业务数据按父分类过滤时，在数据库内计算子孙分类。
5. 所有使用分类的页面共用同一套懒加载组件和接口。
6. 对单个父节点下存在大量直接子节点的极端场景提供分页扩展能力。

## 3. 总体设计

```text
分类管理页/分类选择器
        |
        | 首次打开：parentId=0
        | 展开节点：parentId=当前节点ID
        | 搜索：keyword=关键词，limit<=100
        v
CategoryController
        |
        v
SysCategoryMapper
        |
        +-- 按父节点查询直接子节点
        +-- 按名称前缀查询搜索结果
        +-- 递归 CTE 查询删除子树
        v
sys_category
```

当前方案不会在页面首次打开时加载 10 万叶子节点：

```text
首次加载       -> 只查询根节点
展开节点       -> 只查询该节点的直接子节点
搜索           -> 后端最多返回 100 条
链路分类过滤   -> MySQL 递归计算子孙节点
执行记录过滤   -> MySQL 递归计算子孙节点
```

## 4. 前端设计

### 4.1 统一组件

统一使用：

```text
auto-test/frontend/src/components/CategoryTree.vue
```

使用页面：

- 分类管理
- 链路列表
- 执行记录
- 定时任务
- 链路编辑/新增分类选择

### 4.2 懒加载

TDesign Tree 使用 `children: true` 标记可懒加载节点：

```javascript
{
  id: 1,
  categoryName: '用户管理',
  hasChildren: true,
  children: true
}
```

展开时才调用：

```http
GET /api/category/tree?parentId=1
```

前端同时启用固定高度和虚拟滚动，避免大量已加载节点创建完整 DOM。

### 4.3 服务端搜索

所有分类选择器都显示搜索框，搜索不再依赖客户端递归过滤。

```http
GET /api/category/tree?keyword=订单&limit=100
```

搜索约束：

- `limit` 服务端强制限制在 1 到 200 之间，前端默认 100。
- 当前使用名称前缀匹配：`category_name LIKE '关键词%'`。
- 前缀匹配可以使用名称索引，适合大数据量场景。
- 搜索结果直接作为平铺结果展示，不加载命中节点的完整祖先树。
- 后续可增加 `categoryPath` 字段，用于显示完整路径。

### 4.4 前端禁止做的事情

以下行为禁止在 10 万节点场景使用：

- 请求 `/category/tree` 后在浏览器递归构造完整树。
- 使用 `expand-all=true`。
- 使用全量 `JSON.stringify` 或深度 `watch` 监听分类树。
- 将所有分类 ID 拼接成超长查询参数。
- 在每个页面单独实现分类树加载逻辑。

## 5. 后端接口设计

### 5.1 获取根节点或直接子节点

```http
GET /api/category/tree
```

参数：

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `parentId` | 否 | 父节点 ID，缺省按根节点 `0` 查询 |
| `keyword` | 否 | 分类名称前缀搜索关键词 |
| `limit` | 否 | 搜索结果上限，默认 100，最大 200 |

响应节点包含：

```json
{
  "id": 1,
  "parentId": 0,
  "categoryName": "用户管理",
  "sortOrder": 1,
  "status": 1,
  "hasChildren": true
}
```

### 5.2 创建、修改、删除

创建和修改只操作单个节点，不重新提交整棵树：

```http
POST /api/category/create
PUT /api/category/update?id={id}
DELETE /api/category/delete?id={id}
```

删除子树使用 MySQL 8 `WITH RECURSIVE` 查询后代 ID，再按 500 条一批删除，避免逐节点递归查询。

### 5.3 诊断日志

分类链路统一使用 `[CATEGORY_DIAG]` 前缀，记录：

- 创建请求参数和生成 ID。
- 根节点/子节点查询的 `parentId`。
- 返回节点数量。
- 每个节点的 `id`、`parentId`、`hasChildren`。
- 前端懒加载请求和响应。

## 6. 业务过滤设计

### 6.1 链路列表

用户选择父分类时，链路列表应包含该分类下所有子孙分类的链路。

不在 Java 中查询和拼接所有后代 ID，而是由 MySQL 递归 CTE 计算：

```sql
AND category_id IN (
  WITH RECURSIVE category_scope AS (
    SELECT id
    FROM sys_category
    WHERE id IN (?, ?)
      AND status = 1
    UNION ALL
    SELECT child.id
    FROM sys_category child
    INNER JOIN category_scope parent ON child.parent_id = parent.id
    WHERE child.status = 1
  )
  SELECT id FROM category_scope
)
```

涉及文件：

```text
backend/src/main/resources/mapper/TestChainMapper.xml
```

### 6.2 执行记录

执行记录按分类查询时，同样通过链路表关联分类，再使用递归 CTE 计算子孙分类，避免只匹配父节点本身。

涉及文件：

```text
backend/src/main/resources/mapper/TestExecuteMainMapper.xml
```

### 6.3 分页

业务列表必须使用数据库分页：

- 链路列表：按页查询。
- 执行记录：按页查询。
- 分类下链路：默认只查询第一页，禁止固定拉取 10 万条。

## 7. 数据库设计与索引

分类表继续使用邻接表模型：

```text
sys_category.id
sys_category.parent_id
sys_category.category_name
sys_category.sort_order
sys_category.status
sys_category.tenant_id
```

核心索引：

```sql
KEY idx_category_tree
  (tenant_id, parent_id, status, sort_order, id)

KEY idx_category_name_prefix
  (category_name)
```

业务表已有 `test_chain.category_id` 索引，用于分类过滤。

## 8. 极端场景增强：单父节点 10 万直接子节点

当前懒加载方案解决的是“整棵树不一次加载”，但如果一个父节点直接拥有 10 万个子节点，单次展开仍可能返回大量直接子节点。因此需要继续增加兄弟节点分页。

推荐接口：

```http
GET /api/category/children
  ?parentId=1
  &pageSize=200
  &cursor=...
```

响应：

```json
{
  "list": [],
  "hasMore": true,
  "nextCursor": "..."
}
```

实现要求：

1. `pageSize` 最大 200。
2. 使用 `(sort_order, id)` 游标分页，禁止深度 `OFFSET`。
3. 前端在节点末尾显示“加载更多”，继续向同一节点追加数据。
4. 不使用一次性返回全部兄弟节点的接口。
5. 统计子节点数量使用单独的 `COUNT` 或异步统计，不阻塞首次展开。

这是对极端高扇出分类树的最后一道保护，不能仅依赖虚拟滚动解决。

## 9. 缓存与一致性

当前可以先使用前端组件级缓存：

```text
cache[parentId] = 直接子节点列表
```

新增、修改、删除、排序后：

- 失效当前父节点缓存。
- 删除子树时失效目标节点及其祖先缓存。
- 搜索结果不长期缓存，避免新增分类后搜索不一致。

后续高并发场景可增加 Redis：

```text
category:children:{tenantId}:{parentId}
```

缓存只保存直接子节点，不缓存完整 10 万节点树。

## 10. 性能验收指标

使用 10 万叶子节点、至少 5 级层级、100 万条链路数据进行验收：

| 场景 | 目标 |
| --- | --- |
| 分类管理首屏 | 不返回叶子节点，响应体小于 200 KB |
| 展开普通节点 | P95 小于 300 ms |
| 分类前缀搜索 | P95 小于 500 ms，最多返回 100 条 |
| 链路分类过滤 | 不产生超长 IN 参数，P95 小于 1 s |
| 执行记录分类过滤 | 使用索引和递归查询，P95 小于 1 s |
| 浏览器首屏分类节点 | 小于 500 个 DOM 行 |
| 单父节点高扇出 | 单次响应不超过 200 条 |

必须使用 `EXPLAIN ANALYZE` 检查：

- `sys_category(parent_id, status, sort_order, id)` 是否命中。
- `test_chain(category_id)` 是否命中。
- 是否出现全表扫描。
- 是否出现超大临时表或 filesort。
